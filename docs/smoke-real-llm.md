**项目**：面面俱到 · 模拟面试多智能体
**对应任务**：Alpha 冲刺 S4 · 真实模型冒烟回归
**脚本**：`scripts/smoke_real_llm.py`
**记录人**：苏炜康　**记录日期**：2026-11-24

---

## 1. 为什么要有这一步

复盘 B3 指出：`pytest` 里的 173 个用例全部由脚本化假模型驱动，**假模型全绿不代表线上 DeepSeek 能跑通**。
假模型返回的是预先写死的 JSON，它验证的是「编排逻辑对不对」，
验证不了「真实模型在 6 题里会不会输出截断的 JSON、会不会重复出题、会不会把报告写成一段复读」。

这一步就是把整条链路用真模型跑一遍：分析简历 → 岗位建模 → 6 题作答（含追问）→ 交叉拷问 → 报告 → 导出 PDF。

## 2. 怎么跑

脚本**默认 dry-run，不发任何网络请求**；只有显式加 `--run` 才会消耗额度。

```bash
# 只检查配置与工具链（不消耗额度，随时可跑）
python scripts/smoke_real_llm.py

# 真跑，默认 6 题、走 MCP；--local 强制进程内直调
python scripts/smoke_real_llm.py --run
python scripts/smoke_real_llm.py --run --local

# 指定模型与题数，用于性能对比
python scripts/smoke_real_llm.py --run --model deepseek-chat --questions 4
```

| 参数 | 作用 |
| --- | --- |
| `--run` | 真的调用大模型 |
| `--questions N` | 面试题数，默认 6 |
| `--model` | 覆盖 `OPENAI_MODEL`，用于对比 `deepseek-chat` / `deepseek-flash` |
| `--local` | 强制 `LocalTools`，不启动 MCP 子进程 |
| `--timeout` | 单次模型调用超时，默认 60 秒 |
| `--out` | 实测记录 JSON 的输出目录，默认 `reports/`（已在 `.gitignore`） |

退出码：`0` 全部断言通过，`1` 有断言失败，`2` 配置不可用（缺 Key / 工具层起不来）。

## 3. 脚本判定什么

脚本自带样例简历与 JD，与界面「填入示例简历 / 示例 JD」同源，不读取任何用户文件。
三段回答轮流使用，并刻意避开 `agent/intent.py` 的系统反馈关键词——否则自己的回答会被意图过滤挡回。

跑完后逐条断言，不通过即退出码 1：

| 断言 | 依据 |
| --- | --- |
| API Key 已配置 | `LLMConfig.configured`（占位符与含空白/非 ASCII 的 Key 判为未配置） |
| 工具层可用 | 真调一次 `check_resume_quality` / `match_competencies` / `detect_industry` |
| 流程走到 `DONE` | `session.phase == Phase.DONE` |
| 完成 N 题 | `len(session.turns) >= N`（追问不计数） |
| 首轮分析 ≤20 秒 | 需求 N5 |
| 总分在 0–5 | `report_data["overall_score"]` |
| 结论非空 | `report_data["verdict"]` |
| 行动清单恰好 3 条 | 需求 F8 验收标准 3 |
| 交叉拷问已执行且合并分在 0–5 | 需求 F7 验收标准 2 |
| 报告导出成功 | `export_report` / `export_report_pdf` 落盘到 `workspace/` |
| PDF 内嵌中文字体 | 字节流含 `/FontFile2` 且 >16 KB（与 `tests/unit/test_pdf_font.py` 同一判据） |

耗时口径独立于性能实测（S5）：

- **首轮分析**：`orchestrator.start()` 全程，含简历分析 + 岗位建模两次调用和本地缺口匹配；
- **单题**：`orchestrator.answer()` 一次提交，含「打分 + 出题」两次并行调用（命中预取时只剩打分）；
- **末题到报告**：单独记 `finish_seconds`，里面是 3 次交叉拷问 + 1 次报告生成，
  与「单题」不是同一件事，**不拿去和 3 秒比**。

### 4.3 与 S5 云端实测的对照

S5（`docs/stability-check.md` V5）测的是**云端浏览器里的端到端体验**，
本脚本测的是**本机到 DeepSeek 的纯引擎链路**，两者口径不同：

| 差异 | S5 云端实测 | S4 脚本实测 |
| --- | --- | --- |
| 计时起点/终点 | 点按钮 → 页面出现下一题 | 函数调用进 → 函数调用出 |
| 包含网络往返 | 是（浏览器 ↔ Streamlit Cloud） | 是（本机 ↔ DeepSeek API），但少了浏览器与云端一跳 |
| 包含界面渲染 | 是 | 否 |

因此脚本的数字**通常比云端略快**。答辩时引用性能数据一律用 S5 的云端数字；
本脚本的数字用于回答「引擎本身有没有问题」。

## 5. 已知局限

1. **不能替代人工验收**：脚本只判断结构与数值范围，判断不了「题出得好不好」。
   题目质量需要在界面里真看一眼，属于 S8 / S11 的答辩材料准备。
2. **消费额度**：一次 `--run` 约 18 次调用（追问或去重重试会更多），
   实测前先确认 Key 还有额度。
3. **模型漂移**：同一份脚本在不同日期跑，数字会有波动，
   所以记录必须带日期和模型名，不能只写「实测 3.5 秒」。
4. **回答是固定的**：三段回答轮流使用，模型若针对同一段回答追问两轮以上，
   脚本可能用相近的内容再答一次——这是脚本的简化，不代表产品行为。
