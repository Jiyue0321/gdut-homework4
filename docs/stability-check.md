## 2. 操作步骤（按顺序做，不要跳）

### 第 0 步 · 准备（2 分钟）

1. 手机打开**秒表**，或电脑上用 <https://time.is/stopwatch>。
2. 关闭浏览器里所有 `interview-agent-test.streamlit.app` 的标签页。
3. **等 15 分钟不要访问该地址**——免费实例要闲置一段时间才会休眠，刚访问过测不出冷启动。
   如果期间有别人访问，你测到的会是热启动，**结果作废**，重新等。

### 第 1 步 · 测冷启动（V1）

1. 秒表归零，**按下开始**。
2. 在地址栏输入 <https://interview-agent-test.streamlit.app> 回车。
3. 看到页面出现下面**任意一个**状态时，**按下停止**：
   - 出现「填入示例简历」「填入示例 JD」两个按钮 → 这是**冷启动完成**，记这个时间
   - 出现「Your app is waking up」或转圈动画 → 这是**开始唤醒**，继续等，等它变成上面那样
4. 把秒表读数填进 §3 的 V1。

> 记录两个数字更准：
> - **T1**：从回车到出现「waking up」提示（几乎为 0，可以不算）
> - **T2**：从回车到出现「填入示例简历」按钮 ← **这个才是要填的冷启动耗时**

### 第 2 步 · 测首屏可用性（V2）

页面出来后，**不要点任何按钮**，先看：

1. 页面顶部标题是不是「面面俱到 · 模拟面试多智能体」？
2. 有没有**红色**的报错框？特别是下面两种：
   - 「未配置大模型 API Key。请在 `.env` 中把 `OPENAI_API_KEY` 换成真实 Key…」
   - 「工具服务出错：…」
3. 把看到的红框文字**原样复制**到 §3 的 V2 备注里。没有红框就写「无」。

### 第 3 步 · 跑一次完整面试（V3 + V5）

按下面的点击顺序，**一步一步来**：

| 序  | 点哪里                                     | 预期看到                                           |
| --- | ------------------------------------------ | -------------------------------------------------- |
| 1   | 左栏「填入示例简历」按钮                   | 左边大文本框里出现一段带「广东工业大学」的简历     |
| 2   | 右栏「填入示例 JD」按钮                    | 右边大文本框里出现一段「后端开发实习生」的 JD      |
| 3   | 「岗位名称」输入框 → 输入 `后端开发实习生` | —                                                  |
| 4   | 「目标行业」下拉 → 选 `自动`               | 保持默认即可                                       |
| 5   | 「开始面试」按钮                           | 转圈「面试官正在阅读你的简历与岗位要求…」          |
| 6   | **开始计时**，等第一题出现                 | 出现面试官头像 + 一道问题 + 下方「你的回答」输入框 |

**第 6 步计时很重要**：从点「开始面试」到第一题出现，这是首轮分析的耗时（需求 N5 要求 ≤20 秒）。把秒数填进 §3 的 V5-首轮。

接下来**回答 6 题**。每题的操作都一样：

| 序  | 点哪里             | 说明                                        |
| --- | ------------------ | ------------------------------------------- |
| a   | 「你的回答」文本框 | **至少输入 8 个字**，否则会提示「回答太短」 |
| b   | 「提交回答」按钮   | 转圈「面试官正在看你的回答…」               |
| c   | 等下一题出现       | 每题**单独计时**，填进 §3 的 V5-单题        |

**回答内容随便写，但不要用「测试」「报错」「系统」这些词**——系统有个意图过滤，会把这类输入当成「在反馈问题」而拒收，不推进流程。保险起见直接复制这段：

```
我在实习中负责订单模块重构，把下单接口 P99 从 800ms 降到 120ms。具体做法是先用慢查询日志定位到三条没有走索引的 SQL，补了联合索引；然后对热点商品加 Redis 缓存，命中率做到 92%。过程中遇到过缓存和数据库不一致的问题，最后用先更新库再删缓存的方案解决。
```

这段够长，6 题都粘贴同一段也能通过（评分会说什么你就别管了）。

> **注意**：中途可能出现「追问」——同一道题要你再答一次，这是正常设计，**照常提交即可**。
> 也可能出现「交叉拷问」——三位面试官打分，无需输入。

### 第 4 步 · 测 PDF 中文（V4）

1. 6 题答完后，页面会滚到「面试复盘报告」。
2. 往下拉到最底部，找到两个并排的下载按钮。
3. 点**右边**那个「下载复盘报告（PDF）」。
4. 用浏览器或任意 PDF 阅读器打开下载的文件，**翻到第 1 页**。
5. 看标题和正文的中文：

| 现象                   | 判定           | 填什么         |
| ---------------------- | -------------- | -------------- |
| 中文正常显示           | 通过           | 「正常」       |
| 中文变成 `□□□` 或方块  | **失败**，需修 | 「方块」+ 截图 |
| 中文变成乱码 `å¤´é¢`   | **失败**，需修 | 「乱码」+ 截图 |
| 中文完全不显示（空白） | **失败**，需修 | 「缺失」+ 截图 |

### 第 5 步 · 判定 MCP 路径（V3）

这一步**不用你做额外操作**，从第 3 步的结果反推：

- 如果 6 题全部正常出题、正常打分、PDF 能下载 → **MCP 路径在云端可用**，填「通过」
- 如果点「开始面试」后报错「工具服务出错：…」或一直转圈不出来 → **MCP 路径不可用**，填「失败」并把报错原文抄下来

> 如果想明确知道云端当前走的是哪条路径：目前 Secrets 里 `USE_MCP` 未设置，**默认走 MCP**。
> 若 V3 失败，需要在 Streamlit Cloud 的 App settings → Secrets 里加一行 `USE_MCP = "false"`，
> 保存后应用会自动重启，再重跑第 3 步。

> **结论：单题 3.0–3.8 秒，仍未达到 N5 的 ≤3 秒。** 相对修复前的 5–9 秒已下降约 50%，
> 但 6 次测次里只有 1 次达标，且那次正好落在 3.0 秒边界上。这不是偶发抖动——
> 3.5 秒的中位数说明这就是该配置下的稳态水平。
>
> **第 3 次实测**（作答期间预取下一题，云端）：
>
> 仍然压不到 3 秒。**本项就此停止优化，如实记为未达标。**
>
> 已尝试的两轮优化与效果：
>
> | 优化 | 单题耗时 |
> | --- | --- |
> | 原始（合并调用 + 串行） | 5–9 秒 |
> | 拆分打分与出题为并行调用 | 3.0–3.8 秒（云端） |
> | 作答期间预取下一题 | 仍未稳定进入 3 秒 |
>
> 判定：**未达标**。剩余差距来自「打分」这一次调用本身（约 1.6–3 秒，取决于 DeepSeek 响应），
> 已无代码层可压缩空间——再往下只能换更快的模型或降低评分质量，代价大于收益。
>
> 答辩口径建议：把 5–9 秒 → 3.5 秒作为一条**已实施的性能优化**来讲，
> 并说明为什么停在 3.5 秒（瓶颈在外部模型响应时间，不是本系统逻辑）。
> **不要修改 N5 的目标值，也不要在表里挑好看的数字**——被追问细节时站不住。

> **末题那一行不能拿 3 秒去比。** 第 6 题答完后没有「下一题」——槽位用尽即进结题流程
> （`agent/orchestrator.py:225`），这 30 秒里跑的是 3 次交叉拷问打分 + 1 次报告生成，共 4 次模型调用，
> 与前面「1 次打分 + 1 次出题」不是同一件事。需求 N5 只规定了首轮 ≤20 秒和单题 ≤3 秒，
> 结题耗时没有对应指标，因此记「未定指标」而不是「不达标」。

> **单题 5–9 秒超标的根因（代码级，非网络抖动）**：每次提交回答会调用两次模型——
> `orchestrator.py` 的 `interviewers.ask()` 同时产出「打分 + 下一题」，
> 该次产出的题目除触发追问外都被丢弃；随后 `_ask_next_question()` 再完整生成一次下一题。
> 两次调用 `max_tokens` 均为 2048。
>
> **已在 Alpha 冲刺内修复**：打分与出题拆成两次独立调用
> （`interviewers.score()` / `interviewers.next_question()`），并行发起，
> 打分提示带上本题评分要点以保持判分口径一致，出题输出限制在 900 token；
> 再加上作答期间预取下一题（出题不依赖本轮回答）。
> 本地实测（真实 API）：`deepseek-chat` 由 5–9 秒降至 2.3–3.3 秒；
> `deepseek-flash` 带推理 token，即使并行也需 5 秒左右，不建议作为演示模型。

> 如果单题耗时明显超过 3 秒：先看是不是网络问题（换个时段再测一次），
> 仍然超时的，写进 §4 的结论里，**不要偷偷改目标值**——N5 的指标是需求文档定的，
> 测试结果不达标就如实记录，这比造假被查出来强得多。

## 4. 结论与后续动作

**整体判定**：有条件通过

五条主路径全部跑通：冷启动可接受、首屏无报错、MCP 子进程在云端可用、6 题流程含追问与交叉拷问
完整走完且无异常、报告页正常渲染。**两项遗留问题**：

1. **性能未达标**：单题 3.0–3.8 秒，相对 N5 的 ≤3 秒指标仍超标。已从 5–9 秒优化两次，
   剩余瓶颈在外层模型响应时间，代码层已无可压缩空间，本冲刺停止优化，如实记录。
2. **PDF 字体回退**：两次实测均为 15–16 KB，说明中文字体未内嵌；已改为随仓库分发字体，待复测。

判定为「有条件通过」而非「不通过」，因为两个问题都已有明确修复动作与验证手段，
且功能主路径完整可用；若第 3 次复测字体仍不内嵌，则应降为「不通过」。
